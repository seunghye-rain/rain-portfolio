# Commit Convention

이 문서는 커밋 메시지 규칙과, 변경사항을 커밋으로 나누는 기준을 정리합니다. "커밋해줘" 요청을 받았을 때는 이 문서 기준으로 바로 커밋할 수 있어야 합니다.

## 접두사

| 접두사     | 의미                                                       |
| ---------- | ---------------------------------------------------------- |
| `init`     | 프로젝트 초기 세팅                                         |
| `feat`     | 새로운 기능 추가                                           |
| `fix`      | 버그 수정                                                  |
| `docs`     | 문서 변경                                                  |
| `design`   | UI 변경                                                    |
| `refactor` | 프로덕션 코드 리팩토링                                     |
| `test`     | 테스트 추가/리팩토링 (프로덕션 코드 변경 없음)             |
| `chore`    | 빌드 설정, 패키지 매니저 설정 등 (프로덕션 코드 변경 없음) |
| `deploy`   | 배포                                                       |

## 메시지 형식

```txt
{접두사}: {제목}

{본문 (선택, 필요할 때만)}
```

- 제목은 한 줄로 쓰고, 끝에 마침표를 붙이지 않습니다.
- 제목만으로 "무엇을" 바꿨는지 다 드러나지 않거나, "왜" 이 방식을 선택했는지 남겨야 나중에 이해하기 쉬운 경우 본문을 추가합니다. 본문에는 다음을 씁니다.
  - 무엇을 변경했는지
  - 왜 이 방식으로 했는지 (특히 트레이드오프가 있었거나, 선택하지 않은 대안이 있었을 때)

## 커밋을 나누는 기준

여러 관심사가 섞인 변경사항을 커밋할 때는 아래 기준으로 나눕니다.

1. **같은 scope끼리 묶기** — 하나의 커밋은 하나의 목적/관심사만 담습니다. 예를 들어 "툴링 설정 추가"와 "그 설정 기준으로 기존 코드 재포맷"은 원인이 다르므로 별도 커밋으로 분리합니다.
2. **접두사가 곧 scope 힌트** — 위 접두사 표를 기준으로, 같은 접두사가 붙을 변경끼리 우선 묶고 접두사가 달라지면 커밋도 나눕니다. (예: 설정 변경은 `chore`, 그 설정 때문에 갱신한 문서는 `docs`로 별도 커밋)
3. **자동 생성/포맷팅성 변경은 분리** — Prettier 재포맷처럼 도구가 일괄 변경한 내용은 실제 로직 변경 커밋과 섞지 않고 별도 커밋(`chore: Prettier 기준으로 포맷 정리` 등)으로 둡니다.
4. **문서 갱신은 코드 변경과 함께 또는 분리** — 코드 변경 하나에 대한 문서 갱신이면 같은 커밋에 포함해도 되지만, 여러 코드 변경에 걸친 문서 정리라면 별도 `docs` 커밋으로 둡니다.
5. 공통적으로 사소한 변경 사유로 많은 파일을 한번에 수정한 것이 아니라면 파일 당 1개의 커밋을 기본으로 합니다.

## 커밋 절차

1. `git status`, `git diff`로 전체 변경사항을 확인합니다.
2. 위 기준으로 변경 파일을 그룹으로 나눕니다.
3. 그룹별로 필요한 파일만 `git add`한 뒤 커밋합니다. 한 번에 전체를 `git add -A`로 올리지 않습니다.
4. 각 커밋 메시지는 접두사 + 제목, 필요하면 본문까지 작성합니다.
5. 사용자가 명시적으로 요청하지 않았다면 커밋만 하고 push는 하지 않습니다.
